# 会话文件（.stlog）方案 v1

> ⚠️ **已被 v1.3.1 取代**：[会话文件方案-v1.3.1.md](会话文件方案-v1.3.1.md)（推导过程见
> [v1.1](会话文件方案-v1.1.md)、[v1.2](会话文件方案-v1.2.md)、[v1.3](会话文件方案-v1.3.md)）。
> 现行设计：双槽全量快照 + 尾页重写 + 写者互斥/读者共存 + 无 sidecar 索引 + 零 fsync 稳态。
> 本文件仅作历史对照保留。

> 目的：把"历史"从守护进程顺手写的日志，改成**每个开启了记录的标签/会话一个二进制文件**，
> 文件既是实时记录、也是恢复源；离线下 GUI 可只读打开，推送到守护进程后所有权整体移交。
>
> 状态：方案评审中，未开始实现。0.8.3-dev。

---

## 0. 目标 / 非目标

**目标**

1. 一个开启记录的标签/会话 = 一个 `.stlog` 文件；关闭记录保留文件，再开续写同一文件。
2. 离线（守护进程未运行）GUI 拖入文件即只读打开：分页、搜索、导出。
3. 推送是**手动**动作：把文件与会话设置的所有权移交给守护进程；之后 GUI 只经 IPC 操作。
4. 同一文件同时只允许一个进程打开（本地只读、守护进程 live、守护进程 replay 三者互斥）。
5. 导出 `log`（文本行）/ `txt`（解码文本）/ `csv`（结构化列）。
6. 新建会话支持「由文件开始（续写同一文件）」与「离线读取文件（只读）」。

**非目标（v1 不做）**

- 自动推送（守护进程启动不接管已有本地标签）；拖入是否直接推送由 `drop_action` 设置决定。
- 每标签默认录制：默认仍是"不记录、不建文件"。
- 远程守护进程、数据库、压缩/加密、跨文件全局索引、多文件合并。
- 旧 `history/*.log` 的写入与转换（只读兼容）。

## 1. 术语与所有权

| 实体 | 谁持有 | 说明 |
|---|---|---|
| 文件（磁盘） | 无人 / GUI / 守护进程 | 同一时刻只有一个持有者 |
| 本地文件标签 `local-file` | GUI 进程内 | 只读，不经过守护进程 |
| 会话 session | 守护进程 | `kind=live`（有进程写）或 `kind=replay`（只读） |
| 会话设置 | 推送后：守护进程 | 端口参数、模式、记录开关、文件参数 |
| 界面设置 | 永远 GUI | 主题、字体、比例、语言、hex 样式、`drop_action` |

GUI 的 `settings/gui.ini` 只存界面设置；守护进程的 `settings/daemon.ini` 存 `[storage]` 默认值与
最近一次会话参数；文件头存创建时的会话参数快照。

## 2. 文件格式（字段级）

```
文件布局（默认 header_kb = 16，可在创建时配置 4~64）：

0x0000  superblock A  128B  ┐ 两份交替写：seq 更大且 CRC32 正确者生效
0x0080  superblock B  128B  ┘
0x0100  头部区 A      ~7.8KB
0x2000  头部区 B      ~7.8KB
0x4000  记录区起点（recordsOffset 由 superblock 给出，未来可扩）

superblock = magic "SLOG" | version u16 | seq u32 | activeArea u8 |
             flags u32（bit0=clean bit1=payload=raw）| recordsOffset u64 |
             areaSize u32 | areaCRC u32 | superCRC u32 | reserved
```

**头部区 = 可追加的变更日志（"可修改槽位"）**，每条 entry：

```
entry = type u8 | seq u32 LE | len u16 | payload[len] | crc32 u32

type 1 = base        创建快照（JSON，第一条，必须存在）
type 2 = set         通用修改：payload = {"path":"record","value":true}
type 3 = origin      origin 字典新增：{"id":5,"value":"gui-a3f1"}
type 4 = stats       统计快照（entries/lastTs，加速文件列表；丢了可扫描重建）
type 5 = meta        标签/备注等展示信息
```

**头部校验（三层 CRC32）**：只防意外损坏（断电半写、位翻转、坏道），不防篡改。

| 层级 | 覆盖范围 | 校验失败时 |
|---|---|---|
| entry CRC | 该条 `type+seq+len+payload`（不含自身 4 B） | **从这条起停止应用**（变更日志是顺序的，跳过一条会得到错误状态）；压缩时把已应用部分写成新 `base` |
| 头部区 areaCRC | active 区实际使用的字节（存在 superblock 里） | 整区不可信 → 回退到另一份 superblock 指向的旧区（ping-pong 的旧副本） |
| superblock CRC | superblock 前 124 B（含 seq/recordsOffset/areaCRC） | 该份作废，用另一份；两份都坏则拒绝打开（记录区仍可扫描导出） |

算法是标准 CRC32（IEEE，`hash/crc32.ChecksumIEEE`），4 字节；单条 entry 的校验成本可忽略，
整区 7.8 KB 的校验约几微秒。记录区**不逐条加 CRC**：包格式自带长度字段、尾部半包按规则截断，
逐条加 4 B 会让 33 B/条变成 37 B（+12%），不划算；如果以后需要坏块检测，可在 sidecar 索引里
每 512 条存一个聚合 CRC。

读取流程：校验 superblock（两份取 seq 大且 CRC 正确者）→ 校验 active 头部区 areaCRC →
依次应用 entry（遇到坏 entry 即停止，丢弃其后的补丁）→ 得到当前会话状态 → 从 `recordsOffset` 读记录。

**修改流程（只对元数据，不碰记录区）**：
1. 复制 active 头部区到另一区，追加新 entry，`fsync`；
2. 写另一份 superblock（seq+1、activeArea 指向新区、areaCRC），`fsync`。
崩溃最坏是回到上一份 superblock：丢最后一次元数据修改，记录区与旧头部完好。

**压缩**：头部区满时，把当前状态压成一条新的 `base` 写入 inactive 区（丢弃已应用补丁），再翻 superblock。
压缩由首次写满触发，正常使用极难触发（7.8 KB ≈ 上百条修改，而修改只在开关记录、改参数、发现新来源时发生）。

记录格式：

```
记录 = ts u64 LE | dir u8 | len u16（bit15=带 origin）| payload[len] | [originId u8]
dir: 0=system 1=rx 2=tx 3=P1 4=P2
payload: 数据方向 = 原始字节（raw，不再存 hex）；system = UTF-8 文本
originId: 1..254 查头部字典；255 = 回退，后跟 originLen u8 + origin 字符串
```

**compact 设计**（21 B 小帧 → 33 B/条，约为原始数据的 1.6 倍）：

- 载荷存**原始字节**而不是 hex：小帧体积直接减半；`session.history` 等 IPC 仍输出 hex（在守护进程/读取层转换）。
- **origin 字典在头部**（type 3 entry），记录里只存 1 字节 id；首次出现新来源时追加一条
  `{"id":N,"value":"gui-a3f1"}`，不改动已有记录。
- 字典上限 254：溢出后新来源用 `originId=255` 回退为内联字符串（每条约 +14 B），常见场景不会触发。
- 时间戳暂存完整 u64（增量编码留给 v3，收益 4 B/帧）。

`base`（type=1）示例：

```json
{
  "v": 2,
  "uuid": "3f2a9b1c",
  "created": "2026-10-29T14:40:01+08:00",
  "app": "0.8.3",
  "port": "COM12", "baud": 115200, "dataBits": 8,
  "stopBits": "1", "parity": "none", "flow": "none",
  "mode": "single", "portB": null, "baudB": null,
  "encoding": "utf-8",
  "label": "COM12 @ 115200",
  "origins": []
}
```

**哪些字段可变**（头部 entry）

| 可修改（type 2/5） | 说明 |
|---|---|
| `record` | 是否继续记录（开/关） |
| `port/baud/dataBits/stopBits/parity/flow/mode/portB/baudB` | 重连、切换端口、改参数后的最新值 |
| `label` / `notes` | 用户可见名称与备注 |
| `origins[]`（type 3 追加） | 来源字典，id 只增不改 |
| `stats`（type 4） | entries / lastTs 快照 |

不可变：`uuid`、`created`、`app`（创建版本）、`payload` 编码（raw）。

**写入策略（4 KB 批写入）**

```
每条记录 → 内存缓冲（batch_kb，默认 4 KB，页对齐）
  缓冲满 4 KB              → 一次 write()（4 KB 页对齐，60 帧/s 时约 1 次/秒）
  距上次 flush ≥ batch_ms  → 强制 write()（低速率/Modbus 轮询时保证延迟上界）
  停止记录 / 关闭 / 推送 / 导出与搜索前 → 强制 flush
  fsync：默认关；停止记录、关闭、推送移交前各做一次
```

- `batch_ms` 是**最大延时**而不是固定间隔：流量大时由 4 KB 触发，小时由它兜底。
- 崩溃最多丢最后 ≤ `batch_kb` 未刷数据；尾部半条记录按下面规则截断，不会污染已有数据。

其余约定：

- **头可变、记录区只追加**：元数据（记录开关、参数、来源字典、标签）通过头部变更日志就地更新，
  不碰记录区；记录区永远顺序追加，不需要原地改写。
- **尾部半包**：读时跳过；写模式打开时扫描尾部，若最后一条不完整则**截断到最后一条完整记录**并记日志
  （被截断的字节本来就不完整，不会丢有效数据）。
- **索引**：`<file>.idx` sidecar，每 512 条追加一条 `offset u64 | ts u64 | count u32`；
  缺失时扫描 `.stlog` 重建。索引只用于时间定位，丢了不影响正确性。
- **不做轮转**：超过 `max_size_mb` 时**停止记录并告警**（保持"一个标签一个文件"的身份），由用户决定
  新建会话或调大上限。v1 不做 `-2` 分段。
- **可读性**：raw 载荷无法直接 `grep`；人读场景走导出（log/txt/csv），旧 `history/*.log` 仍是 hex。

**容量参考**

- 格式：偏移 u64 → 理论 16 EB；单条记录 ≤ 16 KB（`len` 15 位，含 origin 标志）。
- 固定开销：头部区 16 KB（双 superblock + 双头部区）+ 索引 sidecar（约 20 B/512 条）。
- 文件系统：NTFS/exFAT 不受限；**FAT32 单文件 4 GB − 1 字节**，若 `sessions/` 在 FAT32 上则硬上限 4 GB 并提前告警。
- 默认软上限 `max_size_mb = 512`，达到即停录告警；建议硬上限 4096 MB。
- 增长速率 ≈ 原始字节率 × 1.57（33 B / 21 B）：

| 波特率 | 原始速率 | 文件增长 | 512 MB 可录 | 4 GB 可录 |
|---|---|---|---|---|
| 115200 | 11.5 KB/s | ≈ 18 KB/s | ≈ 8 小时 | ≈ 64 小时 |
| 230400 | 23 KB/s | ≈ 36 KB/s | ≈ 4 小时 | ≈ 32 小时 |
| 921600 | 92 KB/s | ≈ 145 KB/s | ≈ 1 小时 | ≈ 8 小时 |

（4 KB 帧时膨胀约 2 倍，但每帧承载的数据也多，按字节算时长基本不变。）

## 3. 锁与独占

- **要求**：同一文件同时只允许一个进程打开（读也不行）。
- **实现**：
  - Windows：`CreateFileW(dwShareMode=0)` 独占打开；第二个进程得到 `ERROR_SHARING_VIOLATION`。
    （不用 `LockFileEx`：独占 share 更严格，崩溃时由 OS 自动释放，无 `.lock` 残留。）
  - Unix：`os.OpenFile` + `syscall.Flock(LOCK_EX|LOCK_NB)`。
- **模式**：`openRead`（独占只读）/ `openAppend`（独占读写，文件必须已存在或创建）。
- **同一进程**：内存表记录已打开路径，重复打开直接拒绝。
- **错误**：返回 `errFileLocked{path, holderHint}`；GUI 提示"文件已被占用（GUI/守护进程）"。

## 4. 守护进程会话模型

- 现有 `Process`（live）增加 `sessionFile`（写句柄）与 `record bool`。
- 新增 `ReplaySession`：`id = "file-<uuid8>"`、`path`、读句柄、头信息、分页游标。
- 统一历史来源接口 `historySource`：
  - `ringSource`：live 会话，读 5 MB 共享内存环（现有逻辑）。
  - `fileSource`：replay 会话，直接按 `.stlog` 分页（不建环、不占 5 MB）。
- `process.list` 合并两类，条目带 `kind`（`live`/`replay`）、`sessionFile`、`record`、`created`、`entries`；
  replay 条目 `status="replay"`、无 `connected`。
- 同一文件只允许一个会话：打开前查 `fileIndex[path]`，已存在则返回已有 `sessionId`。

## 6. GUI

**新增标签类型**

- `local-file`：离线只读。数据源是 GUI 进程内 reader，不经过守护进程。
- 会话标签：`sessionId` 指向 live 或 replay；replay 标签灰显"回放"，不显示发送区可用状态。

**Wails 绑定（新增）**

```
OpenLocalFile(path) -> {tabId, header, entries, size}
ReadLocalFilePage(tabId, limit, beforeMs, sameTsSkip) -> 与 GetSessionHistory 同形
SearchLocalFile(tabId, keyword, limit, offset) -> 与 SearchHistory 同形
ExportLocalFile(tabId, format, out, fromMs, toMs) -> {path, entries}
PushLocalFile(tabId, mode) -> {sessionId, kind}   // 先释放锁，再让守护进程独占打开
CloseLocalFile(tabId)
```

**拖放**

- `runtime.OnFileDrop`：按 `gui.ini [file] drop_action` 处理——
  - `local`（默认）：开本地只读标签；
  - `push`：调 `history.open`，成功则直接开守护进程标签；失败回退本地并提示。
- 一次拖多个文件：逐个处理，失败的单独提示。

**新建会话页（4 个入口）**

| 入口 | 行为 |
|---|---|
| 单端口 | 现有流程；开记录后才建文件 |
| 端口转发 | 同上 |
| 由文件开始 | 选文件 → 头里的端口参数预填 → 守护进程独占打开并绑定会话；端口可连时建 live 并续写同一文件，连不上则先以 replay 打开 |
| 离线读取文件 | 本地只读标签，不依赖守护进程 |

**界面细节**

- 本地标签角标「本地」，状态栏「离线 · 只读」；发送/端口/自动发送按钮禁用。
- 标签右键菜单增加：推送到守护进程（本地标签）、导出…、在文件夹中显示。
- 设置页新增「会话文件」：`drop_action`、存储目录、默认记录、上限、保留天数。

## 8. 状态机

```
无文件 ──开启记录──▶ recording(live) ──关闭记录/断开──▶ closed(clean|unclean)
   ▲                        │                                  │
   │                        └──── 崩溃/断电 ────────────────────┘
   │                                                           │
   └──── 新建会话（单端口/转发）        closed ──history.open──▶ replay ──push/attach──▶ recording
```

- 本地标签：`local-readonly` ──推送成功──▶ `replay`（守护进程）──attach──▶ `live`。
- 推送是**锁交接**：GUI 先 close+释放，再请求守护进程 open；守护进程失败则 GUI 重新获取锁并提示。
- 记录开关：开 → 无文件则建，有文件则追加；关 → flush+fsync、写 clean 位、关闭、保留文件。

## 9. 设置项

`settings/gui.ini`：

```ini
[file]
drop_action = local     ; local | push
recent_dir =
```

`settings/daemon.ini`：

```ini
[storage]
dir = sessions
record_default = false
max_size_mb = 512
keep_days = 30
batch_kb = 4          ; 写缓冲大小（页对齐），4~64
batch_ms = 200        ; 最大刷盘延时（10~2000，0=每条都刷）
fsync = false         ; 是否每次 flush 都 fsync（SSD 上代价高，默认关）
header_kb = 16        ; 头部区总大小（含双份 superblock），创建时生效，4~64
index_every = 512
```

会话设置（推送后由守护进程持有）：端口参数、single/forward、转发端口、记录开关、导出默认格式。

## 10. 错误与边界

| 场景 | 行为 |
|---|---|
| 文件被 GUI 本地占用，守护进程要开 | `file_locked`，提示"先在 GUI 里推送或关闭标签" |
| 文件被守护进程占用，GUI 拖入 | 若 `drop_action=push` 或点推送 → 复用已有会话；否则提示"已被守护进程接管" |
| 头损坏 / 魔数不对 | 拒绝打开并说明；旧 `.log` 走 legacy 只读路径 |
| 头部两份 superblock 都坏 | 拒绝打开（元数据不可信）；记录区仍可按字节扫描做"救回导出" |
| 头部区写满 | 自动压缩：当前状态压成新 base 写入另一区后翻页，不影响记录区 |
| 元数据修改时崩溃 | 回退到上一份 superblock，只丢最后一次修改；记录区不受影响 |
| 尾部半包 | 读跳过；写模式打开时截断到最后完整记录并记日志 |
| 索引缺失/损坏 | 扫描 `.stlog` 重建 |
| 磁盘满 | 停止记录、会话继续、发事件，状态栏告警 |
| 超大文件 | 按页读 + sidecar 索引定位，不整文件进内存 |
| 推送失败 | GUI 重新获取锁、标签留在本地只读、提示原因 |

## 11. 兼容与迁移

- 老 `history/*.log`：hex 载荷、无 `SLOG` 头 → 走 legacy 只读路径，可离线打开、可 replay、可导出；
  不可作为 live 追加目标。
- 新 `.stlog`：raw 载荷 + origin 字典；IPC 输出仍统一 hex（在守护进程/读取层转换），
  前端与 CLI 看到的 JSON 形状不变。
- `history.attach`（现有）保留，行为等价于「由文件开始」的 replay 分支。
- 不自动转换历史文件；需要时用 `export` 转 csv/txt 再迁。

## 12. 测试计划

**单元**：superblock 双份与 CRC（坏一份用另一份、两份都坏则拒绝）；头部 entry 应用（base → set → origin →
stats 的顺序语义、坏 entry 起停止应用、seq 乱序拒绝）；头部压缩（写满后压成新 base，旧补丁不再生效）；
记录解析（raw 载荷、system 文本、origin 字典 id 与 255 回退、半包、坏包）；
origin 字典新增（同 id 不重复、上限 254 后转内联）；索引生成/重建；
锁竞争（两进程打开同一文件，第二个必须失败）。

**批写入**：缓冲满 4 KB 触发一次 write；`batch_ms` 到期强制 flush（用可注入时钟测）；
停止/关闭/推送/导出前必 flush；模拟崩溃只丢 ≤ `batch_kb` 尾部数据；写模式打开时截断半条记录。

**集成**：守护进程建会话→开记录→写→关→重开续写；`history.open` replay 分页；推送（GUI 释放→守护进程获取）；
CLI/MCP 检索打开；GUI 拖入离线只读 + 导出；文件头参数预填「由文件开始」；同一文件二次打开被拒。

**性能**：230400 baud 合包后 ~60 帧/s 连续写 1 小时（约 21 万条、约 7 MB）观察 CPU/延迟与 flush 次数；
1 GB 文件分页与流式导出；`batch_kb=4/16` 与 `batch_ms=0/100/500` 的组合对比。

## 14. 风险与待定

1. **`process.list` 混入 replay** 对现有 `syncDaemonSessions` 的改造量（GUI 目前把所有进程当会话标签处理）。
2. **Windows 独占打开**在杀毒软件、网络盘、同步盘下的行为需实测；`CreateFileW(share=0)` 可能被安全软件拦截。
3. **写路径性能**：`batch_kb`/`batch_ms` 的具体取值需在 230400 baud 压测；`fsync=true` 在 SSD 上可能成为瓶颈，默认关。
4. **replay 是否建环**：建议不建，直接文件分页；前端分页接口需要新增本地/文件两种数据源。
5. **大文件导出**时间与内存（建议流式 + 进度事件）。
6. **“由文件开始”的端口参数预填**：文件头参数可能过时，连接前允许用户改。
7. **raw 载荷不可 grep**：人读依赖导出；若后续需要外部工具直接解析，补一份 RFC 风格格式规范。
8. **origin 字典上限 254**：长时间运行、GUI 频繁重连可能溢出，已用 `originId=255` 内联回退（每条约 +14 B），需实测触发频率。
9. **头部就地改写**：每次元数据修改要整区复制（默认 ~7.8 KB）再翻 superblock；元数据改动低频（开关记录、
   改参数、新来源），但需用夹具覆盖"翻页前崩溃""两份 superblock 都坏""压缩写到一半崩溃"三种恢复路径。
10. **头部空间开销**：默认 16 KB/文件；大量短会话（几十 KB 的记录）时占比偏高，可通过 `header_kb=4` 降低。
