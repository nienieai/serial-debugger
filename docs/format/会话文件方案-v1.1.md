## 0. 目标 / 非目标

**目标**

1. 一个开启记录的标签/会话 = 一个 `.stlog` 文件；关闭记录保留文件，再开续写同一文件。
2. 离线（守护进程未运行）GUI 拖入文件即只读打开：分页、搜索、导出。
3. 推送是**手动**动作：把文件与会话设置的所有权移交给守护进程；之后 GUI 只经 IPC 操作。
4. 同一文件**写者唯一**；读者可并发（含杀毒/备份/我们自己的导出）。见 §3。
5. 导出 `log`（文本行）/ `txt`（解码文本）/ `csv`（结构化列）。
6. 新建会话支持「由文件开始（续写同一文件）」与「离线读取文件（只读）」。

**非目标（v1 不做）**

- 自动推送（守护进程启动不接管已有本地标签）；拖入是否直接推送由 `drop_action` 设置决定。
- 每标签默认录制：默认仍是"不记录、不建文件"。
- 远程守护进程、数据库、压缩/加密、跨文件全局索引、多文件合并。
- 旧 `history/*.log` 的写入与转换（只读兼容）。
- **sidecar 索引文件**（v1.1 决定：打开时扫描建内存索引，见 §2.8）。
- **文件预分配、mmap 写入、压缩卷/EFS/网络盘上的写模式**（见 §2.7、§3）。

**一条贯穿全局的原则**：稳态下**零 fsync、每次 write() ≥ 4 KB 且页对齐、写调用次数越少越好**。
所有格式与流程取舍都服从这条；牺牲一点写入时延与元数据实时性来换写放大，可以接受；
牺牲数据完整性来换性能，不可以接受。

## 1. 术语与所有权

| 实体 | 谁持有 | 说明 |
|---|---|---|
| 文件（磁盘） | 无人 / GUI / 守护进程 | **写者唯一**；读者可并发（§3） |
| 本地文件标签 `local-file` | GUI 进程内 | 只读，不经过守护进程 |
| 会话 session | 守护进程 | `kind=live`（有进程写）或 `kind=replay`（只读） |
| 会话设置 | 推送后：守护进程 | 端口参数、模式、记录开关、文件参数 |
| 界面设置 | 永远 GUI | 主题、字体、比例、语言、hex 样式、`drop_action` |

GUI 的 `settings/gui.ini` 只存界面设置；守护进程的 `settings/daemon.ini` 存 `[storage]` 默认值与
最近一次会话参数；文件头存创建时的会话参数快照。

## 2. 文件格式（字段级）

### 2.1 布局

```
header_kb = 16（默认；创建时可配 4 / 8 / 16 / 32 / 64）

0x0000  superblock A      128 B   ┐ 两份交替写：seq 更大且校验通过者生效
0x0080  superblock B      128 B   ┘
0x0100  头部区 A         7936 B   ┐ areaSize = recordsOffset/2 - 256
0x2000  头部区 B         7936 B   ┘
0x4000  记录区起点 recordsOffset = header_kb * 1024，恒为 4 KB 倍数
```

对齐算式：`recordsOffset = header_kb*1024`，`areaSize = recordsOffset/2 - 256`。
header_kb ∈ {4, 8, 16, 32, 64} 时，两个头部区都严格落在 2 KB 与 4 KB 边界内，`recordsOffset` 恒 4 KB 对齐。

`header_kb` 只在创建时生效，写进 superblock（`areaSize`/`recordsOffset` 字段），后续打开以文件为准。

### 2.2 superblock（128 B）

```
magic "SLOG" u32 | version u16 | activeArea u8 | flags u8
| seq u64 | recordsOffset u64
| areaSize u32 | usedBytes u32
| areaCRC u32 | reserved[88]
| superCRC u32                     ← 最后 4 B，覆盖前 124 B
```

- `version`：v1 = 1。读到更高版本直接拒绝打开（提示"由更新版本创建"），不做猜测兼容。
- `flags`：bit0 = `clean`（干净关闭）；bit1 = `payload_raw`（必须为 1）；bit2–7 保留**必须为 0**。
- `activeArea`：0 = 头部区 A，1 = 头部区 B。
- `usedBytes`：active 区实际使用的字节数，`areaCRC` 只覆盖这 `usedBytes` 字节。
- `seq`：u64 单调递增（每次翻 superblock +1）。4.29e9 次/秒也要 136 年，不做回绕处理；
  万一 `seq` 到顶，压缩时重置为 1 并同时把 `usedBytes`/区内容整体重写（压缩本身已自带）。

### 2.3 头部变更日志（"可修改槽位"）

```
entry = type u8 | idx u16 LE | len u16 LE | payload[len] | crc32 u32
crc32 覆盖 type + idx + len + payload（不含自身 4 B）
idx   = 区内下标，从 0 开始连续递增（不是全局 ID，不跨区比较，不参与回绕）
len   ≤ 4096（单条 entry 硬上限，base 也不许超）
```

| type | 名称 | 载荷 | 写入时机 |
|---|---|---|---|
| 1 | `base` | 创建快照 JSON（**必须是第一条**） | 建文件、压缩 |
| 2 | `set` | `{"path":"record","value":true}` | 开关记录、改端口参数 |
| 3 | `origin` | `{"id":5,"value":"gui-a3f1"}` | 首次出现新来源（会话内至多 254 次） |
| 4 | `stats` | `{"entries":N,"lastTs":T}` | **仅** 关闭 / 压缩 / 推送移交前，且距上次 ≥ 60 s |
| 5 | `meta` | 标签、备注等展示信息（单字段 ≤ 1 KB） | 用户改名/写备注 |

`base`（type=1）示例：

```json
{
  "v": 2,
  "uuid": "3f2a9b1c",
  "created": "2026-10-29T14:40:01+08:00",
  "app": "0.8.3",
  "port": "COM12", "baud": 115200, "dataBits": 8,
  "stopBits": "1", "parity": "none", "flow": "none",
  "mode": "single", "portB": null, "baudB": null,
  "encoding": "utf-8",
  "label": "COM12 @ 115200",
  "origins": []
}
```

**哪些字段可变**

| 可修改（type 2/3/5） | 说明 |
|---|---|
| `record` | 是否继续记录（开/关） |
| `port/baud/dataBits/stopBits/parity/flow/mode/portB/baudB` | 重连、切换端口、改参数后的最新值 |
| `label` / `notes` | 用户可见名称与备注 |
| `origins[]`（type 3 追加） | 来源字典，id 只增不改；同一 origin 字符串不重复占号 |
| `stats`（type 4） | entries / lastTs 快照，仅在 §2.3 表的时机写 |

不可变：`uuid`、`created`、`app`（创建版本）、`payload` 编码（raw）。

### 2.4 头部校验与合法性校验

**三层 CRC32**（标准 IEEE 多项式，`hash/crc32.ChecksumIEEE`）：只防意外损坏（断电半写、位翻转、坏道），
不防篡改。目的决定算法：CRC32 足够快（整区 7.9 KB 约几微秒）、开销只有 4 B，用 SHA 没有额外价值。

| 层级 | 覆盖范围 | 校验失败时 |
|---|---|---|
| entry CRC | 该条 `type+idx+len+payload` | **从这条起停止应用**（变更日志顺序生效，跳过一条会得到错误状态）；写模式下立即压缩修复（§2.5） |
| 头部区 areaCRC | active 区前 `usedBytes` 字节 | 整区不可信 → 回退到另一份 superblock 指向的旧区（ping-pong 的旧副本） |
| superblock superCRC | superblock 前 124 B（含 seq/recordsOffset/areaCRC） | 该份作废，用另一份；两份都坏则拒绝打开（记录区仍可扫描导出） |

**合法性校验（v1.1 新增，逐字段硬规则）**——CRC 只能证明"没坏"，不能证明"合理"：

| 字段 | 规则 | 违反时 |
|---|---|---|
| `magic` | == `"SLOG"` | 不是本格式（尝试 legacy 路径，失败则报错） |
| `version` | == 1 | 拒绝打开 |
| `activeArea` | 0 或 1 | 该份作废 |
| `recordsOffset` | 4096..65536、4 KB 对齐、≤ 文件大小、== `header_kb*1024` 的已知取值 | 该份作废 |
| `areaSize` | == `recordsOffset/2 - 256` | 该份作废 |
| `usedBytes` | ≤ `areaSize` | 该份作废 |
| `flags` 保留位 | 必须为 0 | 该份作废 |
| `areaCRC` | 覆盖范围内不匹配 | 该份作废，回退另一份 |
| 两份 `seq` 相等 | 取 `areaCRC` 通过者；都通过取 A | 确定性 tie-break，禁止随机 |

两份都作废 → **拒绝打开**（元数据不可信），记录区仍可做"救回导出"（按 §2.6 逐条扫描，遇坏即停）。

**entry 解析规则**：`idx` 必须严格等于上一条 +1；`len ≤ 4096` 且 `len + 9 ≤ usedBytes - 偏移`
（9 = type 1 + idx 2 + len 2 + crc 4）；
`type ∈ 1..5`；第一条必须是 `base`。任一条不满足 → 停止应用（等同坏 entry）。

### 2.5 修改流程与压缩

```
修改（只对元数据，不碰记录区）：
1. 复制 active 区 → inactive 区，尾部追加新 entry；本步不 fsync
2. 写 inactive 对应的 superblock（seq+1、activeArea 翻转、usedBytes、areaCRC）；fsync 仅当 fsync=true
3. 写失败 → 旧 superblock 继续生效，记日志、报错，但**不停止记录**
崩溃：若新 superblock 已落盘而新区没落盘 → 新区 areaCRC 失败 → 回退旧 superblock + 旧区
      → 状态回退一次修改，记录区完好。这正是"只 fsync 一次"的依据。
```

**压缩（把当前状态压成一条新 `base`）触发条件**（v1.1 从 1 条扩到 3 条）：

1. 区内剩余空间放不下一条最大 entry（≈ 4 KB）；
2. **写模式打开时发现坏 entry**（坏点之后的补丁已永久失效，不压缩会让"用户已停录"等状态丢失）；
3. **干净关闭时 `usedBytes > areaSize/2`**（避免短会话反复开合把头部越攒越大）。

压缩骤死恢复路径（写一半断电）：inactive 区半新半旧 → `areaCRC` 不通过 → 旧 superblock + 旧区仍有效。

### 2.6 记录格式

```
记录 = ts u64 LE | dir u8 | len u16 LE（bit15 = 带 origin）| payload[len] | [originId u8 | 内联]
dir: 0=system 1=rx 2=tx 3=P1 4=P2 0x7F=填充（读取侧跳过）
payload: 数据方向 = 原始字节（raw，不存 hex）；system = UTF-8 文本
len ≤ 16384（bit15 留给 origin 标志，15 位 = 32767，这里主动压到 16 KB）
ts: 写入侧强制单调（now ≤ last 时写 last+1），避免 NTP 回跳把按时间分页搞坏
originId: 1..254 查头部字典；255 = 回退，后跟 originLen u8（≤ 64）+ UTF-8 字符串
```

**填充记录**：`dir=0x7F`、`payload` 全 0、`len` 为填充内容长度。只用于把 EOF 补到 4 KB 边界（§2.7），
不计入条目数、不参与搜索/导出。

**compact 设计（21 B 小帧 → 33 B/条）**

- 载荷存**原始字节**而不是 hex：小帧体积直接减半；`session.history` 等 IPC 仍输出 hex（读取层转换）。
- **origin 字典在头部**（type 3 entry），记录里只存 1 字节 id；首次出现新来源时追加一条，不改动已有记录。
  同一字符串复用同一 id，不重复占号。
- 字典上限 254：溢出后新来源用 `originId=255` 回退为内联字符串（每条约 +14 B），常见场景不会触发。
- 时间戳使用完整 u64。**注意**：增量编码可再省 4 B/帧，但会让崩溃后的记录区扫描失去时间锚点，
  且时间锚点必须依赖头部（头部丢了就没时间），收益（约 4 B/条）不值这个代价，留待 v3 再评估。

### 2.7 写入策略（页对齐 + 批量 + 零 fsync）

```
缓冲 = batch_kb（默认 8 KB，范围 4~64，必须是 4 KB 的倍数）
  缓冲满          → 一次 write()（整段一次系统调用，不拆多段）
  距上次 flush ≥ flush_max_ms（默认 1000；0 = 只在满页/显式动作时写）→ write()
  显式 flush：关闭、停录、推送移交、导出与搜索前、崩溃恢复后
  fsync：默认只在 关闭 / 停录 / 推送移交 三个点；
         [storage] fsync=true 时才每次 flush 后 fsync（SSD 上代价高，默认关）
```

**为什么这么定（写放大的真实来源）**

1. **每次 `write()` 都会让 NTFS 更新文件长度/时间戳并写 `$LogFile`**，代价与调用次数相关、
   与字节数关系不大。所以压调用次数比压字节数更值钱。
2. **页内重写（RMW）**：不到 4 KB 的追加会反复重写同一个 4 KB 页。低速率设备（200 B/s Modbus 轮询）时：

| `flush_max_ms` | 每次写 | 同一页被写回 | 物理放大 |
|---|---|---|---|
| 200（v1 隐含） | ~40 B | ≈25 次 | **≈25×**（4 KB/s 换 200 B/s） |
| 1000 | ~200 B | ≈5 次 | ≈5× |
| 5000 | ~1 KB | ≈4 次 | ≈4× |
| 0（满页才写） | 4 KB | 1 次 | **1×**，代价是 ≤21 s 的数据窗口 @200 B/s |

（回写间隔取量级：Windows 脏页回写数秒级，Linux `dirty_writeback` 默认 5 s / `dirty_expire` 30 s。
上表只用来说明量级，不精确到毫秒。默认取 1000 是"≤1 s 可见"与"≈5× 放大"的折中；
纯长时间泡机、可接受长窗口的场合建议设 0。）

3. **页对齐怎么维持**：`recordsOffset` 4 KB 对齐 + `batch_kb` 是 4 KB 倍数 + 每次整段写 →
   正常追加全程对齐。**唯一破界点是关闭时那次不满页的 flush**。
4. **续写补齐对齐**：`openAppend` 后先写一条填充记录，把 EOF 补到下一个 4 KB 边界
   （所需字节 < 11 B 时再多补 4 KB，保证能容纳一条记录的 11 B 头）。成本 ≤ 4 KB / 次开会话，
   换整场 1× 写放大。读取侧按 `dir=0x7F` 跳过。
5. **显式不做**：
   - 预分配（`SetEndOfFile`/`fallocate` 预留 512 MB 等于立刻写 512 MB 零）；
   - `mmap` 写入（脏页回写时机不可控，写放大不可控）；
   - 写到压缩卷 / EFS / 网络盘（检测到则告警；写模式默认拒绝，见 §3）。
6. **稳态代价**：零 fsync、每次写入 ≥4 KB 且页对齐、一次系统调用。
   115200 合包后约 12.3 KB/s → `batch_kb=8` 时约 **1.5 次写/秒**。

**其余约定**

- **头可变、记录区只追加**：元数据通过头部变更日志就地更新，不碰记录区；记录区永远顺序追加。
- **尾部半包**：读时跳过；写模式打开时按 §2.9 截断到最后一条完整记录。
- **不轮转**：超过 `max_size_mb` 停止记录并告警（保持"一个标签一个文件"的身份），由用户决定
  新建会话或调大上限。
- **可读性**：raw 载荷无法直接 `grep`；人读场景走导出（log/txt/csv），旧 `history/*.log` 仍是 hex。

### 2.8 索引：无 sidecar（v1.1 变更）

v1 的 `<file>.idx`（每 512 条一条 20 B 记录）在 115200 下约 1 次/秒写入，
但因为**每次写都至少落一个 4 KB 页**，物理代价 ≈ **+24% 写放大**，还额外带来：
一个句柄、一个文件、一类"索引条目必须晚于其记录落盘"的一致性约束、一条"索引损坏"错误路径。

v1.1 改为：**打开时顺序扫描记录区，在内存里建索引**——每 512 条记一个锚点
`{offset, ts, n}`，索引只服务时间定位与分页，不落盘。

- 扫描成本：512 MB ≈ 0.5 s、4 GB ≈ 4 s（SSD 冷缓存，顺序读）；
- 每次打开都重建，因此**不存在"索引损坏/缺失"这种状态**；
- 关闭/崩溃都不需要维护索引，少一整类故障；
- 若以后实测"超大文件打开太慢"，再引入**可选**的 `index_every_kb`（默认关闭），
  并且那时应该做成文件内检查点记录而不是 sidecar。

### 2.9 崩溃恢复

```
写模式打开（openAppend）：
1. 校验两份 superblock（§2.4）→ 得到元数据状态
2. 置 clean=0 并落盘（这一次 fsync，用来标记"可能不干净"）
3. 扫描尾部：不完整记录截断到最后一条完整记录（SetEndOfFile + fsync）
4. 若头部存在坏 entry → 立即压缩成新 base（§2.5 触发条件 2）
5. 写填充记录，把 EOF 补到 4 KB 边界（§2.7）
6. 开始追加
关闭（停录/关闭标签/推送移交）：flush → fsync → 必要时压缩 → clean=1 → 关闭句柄
```

- 截断与压缩都是幂等的：中途再崩，下次打开重跑一遍即可。
- 读模式（含并发读）遇到 `clean=0` 只做提示（"上次未正常关闭"），**不写入、不修复**。
- 顺序要求：先截断后翻 superblock，否则会出现"superblock 说干净但尾部还是半条"。

### 2.10 容量与上限

- 偏移 u64 → 理论 16 EB；单条记录 ≤ 16 KB。
- 固定开销：头部 16 KB / 文件（双 superblock + 双头部区），无 sidecar。
- 文件系统：NTFS/exFAT 不受限；**FAT32 单文件 4 GB − 1 字节**，`sessions/` 在 FAT32 上时硬上限 4 GB 并提前告警。
- 默认软上限 `max_size_mb = 512`（达到即停录告警），建议硬上限 4096 MB。
- 增长速率：**合包后 ≈1.01–1.07×**，逐帧成条（最坏）≈1.57×（= 33 B / 21 B）。

| 波特率 | 原始速率 | 合包后（16 ms 窗口） | 逐帧（最坏） | 512 MB 可录（合包 / 逐帧） | 4 GB 可录（合包 / 逐帧） |
|---|---|---|---|---|---|
| 115200 | 11.5 KB/s | ≈12.3 KB/s（1.07×） | ≈18.1 KB/s（1.57×） | 12.2 h / 8.2 h | 97 h / 66 h |
| 230400 | 23.0 KB/s | ≈23.8 KB/s（1.03×） | ≈36.2 KB/s（1.57×） | 6.3 h / 4.1 h | 50 h / 33 h |
| 921600 | 92.2 KB/s | ≈92.9 KB/s（1.01×） | ≈144.8 KB/s（1.57×） | 1.6 h / 1.0 h | 12.8 h / 8.2 h |

（v1 表格按 1.57× 算，实际守护进程合包后是 1.01–1.07×，容量整体放宽约 1.5 倍；
本表两种口径都列，避免以后再算错。）

## 3. 锁与独占（v1.1 变更：写者互斥、读者共存）

**问题**：v1 要求 `CreateFileW(share=0)`（连读都不许）。这会把杀毒扫描、备份、系统搜索索引
全部挡在门外——这些程序拿不到读句柄时，部分安全产品会拦截或反复重试，把"安全设计"变成"兼容性故障"。

**v1.1 规则**

```
Windows
  写者：CreateFileW(GENERIC_READ|GENERIC_WRITE, dwShareMode = FILE_SHARE_READ)
  读者：CreateFileW(GENERIC_READ,               dwShareMode = FILE_SHARE_READ|FILE_SHARE_WRITE)
Unix
  写者：O_RDWR|O_CREATE + flock(LOCK_EX|LOCK_NB)
  读者：O_RDONLY        + flock(LOCK_SH|LOCK_NB)
```

- **两个写者仍然必然互斥**：写者的 share 不含 `WRITE`，第二个写请求（需要 `GENERIC_WRITE`）直接被拒。
- 读者可以并发：读方本来就按 §2.4/§2.6 规则容忍半包尾与坏记录，不依赖"文件已关闭"这一前提。
- 附带能力：本地标签可以只读跟随一个正在被守护进程写的文件（可选，每 500 ms 重扫尾部）。
- 不用 `LockFileEx`、不用 `.lock` 文件：崩溃时由 OS 释放，无残留锁。
- **网络盘（UNC）与压缩/EFS 卷**：写模式默认拒绝（`[storage] allow_network_dir=true` 可强行放行），
  读模式允许。理由：SMB 的共享语义、`fsync` 语义与本地文件系统的追加语义都不能保证上述不变量。
- **同一进程**：内存表记录已打开路径，重复写打开直接拒绝（读打开允许）。
- **错误**：`errFileLocked{path, mode, holderHint}`；GUI 文案"文件已被占用（GUI / 守护进程 / 其他程序）"。

## 4. 守护进程会话模型

- 现有 `Process`（live）增加 `record bool` 与 `fileWriter`（写句柄）。**句柄只在单一写协程内使用**。
- 新增 **写协程**（每个录制会话一个）：从 channel 收 `{records, headerChange, flush, close}`，
  负责：按 §2.7 合并刷缓冲、把头部变更合并到 ≤1 次/秒落盘、处理写错误（失败 → 停录 + 事件）。
  这既是并发安全的前提，也是"头部变更合并"落地的地方。
- 新增 `ReplaySession`：`id = "file-<uuid8>"`、`path`、读句柄、头信息、内存索引（§2.8）、分页游标。
- 统一历史来源接口 `historySource`：
  - `ringSource`：live 会话，读 5 MB 共享内存环（现有逻辑）。
  - `fileSource`：replay 会话，按内存索引直接分页（不建环、不占 5 MB）。
- `process.list` 合并两类，条目带 `kind`（`live`/`replay`）、`sessionFile`、`record`、`created`、`entries`；
  replay 条目 `status="replay"`、无 `connected`。
- `fileIndex[path]` → sessionId：同一文件只允许一个会话，重复 `history.open` 返回既有 `sessionId`（`reused=true`）。

## 8. 状态机与锁交接

```
无文件 ──开启记录──▶ recording(live) ──关闭记录/断开──▶ closed(clean|unclean)
   ▲                        │                                  │
   │                        └──── 崩溃/断电 ────────────────────┘
   │                                                           │
   └──── 新建会话（单端口/转发）        closed ──history.open──▶ replay ──push/attach──▶ recording
```

- 本地标签：`local-readonly` ──推送成功──▶ `replay`（守护进程）──attach──▶ `live`。
- 推送是**锁交接**，必须写清时序（v1.1 补充）：

```
local-held ──flush+fsync──▶ releasing(close 句柄) ──▶ history.open
   成功 → daemon-held（之后 GUI 一律走 IPC）
   失败 → 查 history.files：
            file.locked 且被守护进程持有 → 直接开 replay 标签（不重复抢锁）
            否则重试 3 × 200 ms
              仍失败 → 重新获取本地锁，标签留在本地只读，提示"被其他程序占用"
```

- 交接窗口里第三方抢占只可能发生在 `close` 与 `open` 之间，重试 + 查询足以收敛；
  不做 `.lock` 占位文件（崩溃残留的代价比这个窗口大）。
- 记录开关：开 → 无文件则建，有文件则补齐对齐后追加；关 → flush + fsync + 压缩(按需) + clean=1 + 关闭、保留文件。

## 10. 错误与边界

| 场景 | 行为 |
|---|---|
| 文件被其他写者占用 | `file_locked`，提示"文件已被占用（GUI / 守护进程 / 其他程序）" |
| 文件被守护进程占用，GUI 拖入 | 若 `drop_action=push` 或点推送 → 复用已有会话；否则提示"已被守护进程接管" |
| 头损坏 / 魔数不对 | 拒绝打开并说明；旧 `.log` 走 legacy 只读路径 |
| superblock 字段越界（recordsOffset 离谱等） | 该份作废；两份都废则拒绝打开（不 seek、不分配） |
| 头部两份 superblock 都坏 | 拒绝打开（元数据不可信）；记录区仍可按字节扫描做"救回导出" |
| 头部区写满 / 发现坏 entry / 关闭时占用过半 | 自动压缩成新 base 后翻页，不影响记录区 |
| 元数据修改时崩溃 | 回退到上一份 superblock，只丢最后一次修改；记录区不受影响 |
| 尾部半包 / 半条记录 | 读跳过；写模式打开时截断到最后完整记录并记日志 |
| 记录区中间出现坏记录 | 读到该处即停（不猜、不跳），已读部分正常展示 |
| 磁盘满（`ENOSPC`/`DISK_FULL`） | 停录、flush 能写的部分、clean=0、发事件、状态栏告警；文件保持可读可导出 |
| 可用空间 < `min_free_mb` | **写前**检查（每 64 MB 或每 30 s 一次），提前停录并告警，别等写满系统盘 |
| 达到 `max_size_mb` | 在**下一批写入前**停录并告警，不写出超限的那一页 |
| 写入返回 I/O 错误（EIO 等） | 停录、关闭句柄、会话保留但标 `record=false`，事件提示"写盘失败" |
| 推送失败（第三方抢占 / 守护进程拒绝） | GUI 重试 3×200 ms → 重新获取锁、标签留在本地只读、提示原因 |
| 导出失败 | 先写 `*.tmp`，成功后 rename；失败删除 tmp，不留半个文件、不覆盖原文件 |
| 超大文件 | 按页读 + 内存索引定位，不整文件进内存；扫描耗时见 §2.8 |
| 网络盘 / 压缩卷 / EFS | 写模式拒绝（可配放行），读模式允许 |

## 11. 兼容与迁移

- 老 `history/*.log`：hex 载荷、无 `SLOG` 头 → 走 legacy 只读路径，可离线打开、可 replay、可导出；

- `version > 1` 的文件：拒绝打开并提示版本，不做"尽力解析"。

## 12. 测试计划

**单元**

- superblock：双份与 CRC（坏一份用另一份、两份都坏拒绝）；**逐字段合法性表**（`recordsOffset` 越界/
  非对齐、`version=2`、保留位非 0、`usedBytes > areaSize`、`seq` 相等 tie-break）；
- 头部 entry：base → set → origin → stats 顺序语义；`idx` 必须连续；坏 entry 起停止应用；压缩后旧补丁不再生效；
  写模式遇到坏 entry 必须立即压缩；
- 记录解析：raw 载荷、system 文本、`dir=0x7F` 填充跳过、半包、坏包、`len` 越界、origin 255 内联、字典满 254；
- 时间戳：写入侧单调钳制（注入回拨时钟）；
- 容量：达到 `max_size_mb` 时不多写一页；FAT32 口径计算。

**锁**

- 写-写互斥（两进程，第二个必须失败）；
- 写-读并发：读者能在写者持有句柄时打开，读到一半的尾部必须"停"而不是报错；
- 读-读并发；同一进程重复写打开被拒。

**批写入**

- 缓冲满触发一次 writ（断言调用次数，不是字节数）；
- `flush_max_ms` 用可注入时钟测；显式 flush 点（关闭/停录/推送/导出/搜索）；
- 模拟崩溃最多丢 ≤ `batch_kb` 尾部；重开时截断半条；
- **续写对齐**：关闭后 EOF 非 4 KB 对齐，重开必须写填充记录使偏移对齐，读取侧正确跳过；
- `fsync=false` 时稳态 fsync 次数为 0（关闭/停录/移交除外）。

**磁盘与故障**

- 模拟 `ENOSPC`：停录 + 事件 + 文件仍可读可导出；
- 可用空间低于 `min_free_mb` 时提前停录；
- 只读卷 / 无权限目录：建文件失败的错误信息可读、不崩。

**安全**

- 恶意文件（`recordsOffset=0xFFFFFFFFFFFFFFFF`、`len=0xFFFF`、坏 JSON、超长 label、
  `origins` 10 万条、保留名/路径穿越文件名）→ 不崩、不越界、不无限循环；
- CSV 导出对 `= + - @` 开头的单元格加前缀（防公式注入），引号/逗号/换行正确转义；
- 导出走 tmp + rename，失败不留残件。

**集成**

- 守护进程建会话 → 开记录 → 写 → 关 → 重开续写；`history.open` replay 分页；
- 推送（GUI 释放 → 守护进程获取），含"交接窗口被第三方抢占"的失败路径；
- CLI/MCP 检索打开；GUI 拖入离线只读 + 导出；文件头参数预填「由文件开始」；同一文件二次写打开被拒。

**性能**

- 230400 合包后 ~60 包/s 连跑 1 小时：约 **21.6 万条、约 82 MB**（v1 写的 7 MB 是笔误，
  60×3600×396 B ≈ 85 MB）。统计 `write()` 次数（目标 ≤ 1.5 次/s @ `batch_kb=8`）、
  fsync 次数（稳态 0）、CPU 与 UI 延迟；
- 1 GB 文件打开扫描耗时（目标 ≤ 1 s 热缓存）与分页、流式导出；
- `batch_kb=4/8/16` × `flush_max_ms=0/200/1000/5000` 组合对比：记录写调用次数与进程 I/O 计数。

## 14. 风险与待定

1. **`process.list` 混入 replay** 对现有 `syncDaemonSessions` 的改造量（GUI 目前把所有进程当会话标签处理）。
2. **并发读的期望管理**：读者可能读到"半个包"，前端必须表现为"实时追加中"而不是数据错误；
   需要 UI 文案与刷新节奏（500 ms）约定。
3. **冷缓存打开 4 GB ≈ 4 s**：可接受，但如果用户频繁来回切大文件会觉得慢；v2 再评估文件内检查点。
4. **`flush_max_ms=0` 的数据窗口**：低速率下可达 20 s（200 B/s 填满 4 KB）。默认 1000 是折中，
   长时间泡机场景由用户在设置页改。
5. **`write()` 次数**在真实 NTFS 上的收益需实测（表里的 1.5 次/秒是理论值，含合包假设）。
6. **大文件导出**时间与内存（流式 + 进度事件）。
7. **「由文件开始」的端口参数预填**：文件头参数可能过时，连接前允许用户改。
8. **raw 载荷不可 grep**：人读依赖导出；若后续需要外部工具直接解析，补一份 RFC 风格格式规范。
9. **origin 字典上限 254**：长时间运行、GUI 频繁重连可能溢出，已用 `originId=255` 内联回退（每条约 +14 B），需实测触发频率。
10. **头部整区复制**：每次元数据修改复制 ~7.9 KB；已把触发压到"开关记录/改参数/新来源/关闭"这几个低频点，
    但需用夹具覆盖"翻页前崩溃""两份 superblock 都坏""压缩写到一半崩溃"三条恢复路径。
11. **header 16 KB 对短会话占比高**：几十 KB 的记录时头部占三成；可 `header_kb=4` 降到 4 KB。
12. **网络盘/压缩卷直接不支持写**：明确拒绝并提示，不做"尽力而为"。
13. **杀毒软件对 `FILE_SHARE_READ` 的处理**需实测（v1 的 `share=0` 风险已缓解，但换成了另一组行为，仍需真机验证）。
