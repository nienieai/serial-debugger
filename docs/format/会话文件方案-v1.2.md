# 会话文件（.stlog）方案 v1.2

> ⚠️ **已被 v1.3.1 取代**：[会话文件方案-v1.3.1.md](会话文件方案-v1.3.1.md)。
> 后续改动：v1.3 允许尾页整页重写（取代 `dir=0x7F` 填充记录）、Unix 读者不再加锁；

> 目的：把"历史"从守护进程顺手写的日志，改成**每个开启了记录的标签/会话一个二进制文件**，
> 文件既是实时记录、也是恢复源；离线下 GUI 可只读打开，推送到守护进程后所有权整体移交。
>

## 0. 目标 / 非目标

**目标**

1. 一个开启记录的标签/会话 = 一个 `.stlog` 文件；关闭记录保留文件，再开续写同一文件。
2. 离线（守护进程未运行）GUI 拖入文件即只读打开：分页、搜索、导出。
3. 推送是**手动**动作：把文件与会话设置的所有权移交给守护进程；之后 GUI 只经 IPC 操作。
4. 同一文件**写者唯一**；读者可并发（含杀毒/备份/我们自己的导出）。见 §3。
5. 导出 `log`（文本行）/ `txt`（解码文本）/ `csv`（结构化列）。
6. 新建会话支持「由文件开始（续写同一文件）」与「离线读取文件（只读）」。
7. **设置可恢复**：任一槽完好 ⇒ 拿到一份完整自洽的设置；不出现"半个状态"。

**非目标（v1 不做）**

- 自动推送（守护进程启动不接管已有本地标签）；拖入是否直接推送由 `drop_action` 设置决定。
- 每标签默认录制：默认仍是"不记录、不建文件"。
- 远程守护进程、数据库、压缩/加密、跨文件全局索引、多文件合并。
- 旧 `history/*.log` 的写入与转换（只读兼容）。
- **sidecar 索引文件**（打开时扫描建内存索引，见 §2.8）。
- **追加式元数据变更日志 / 头部压缩**（v1.2 改为全量快照，见 §2 开头的取舍说明）。
- **文件预分配、mmap 写入、压缩卷/EFS/网络盘上的写模式**（见 §2.7、§3）。

**一条贯穿全局的原则**：稳态下**零 fsync、每次 write() ≥ 4 KB 且页对齐、写调用次数越少越好**。
所有格式与流程取舍都服从这条；牺牲一点写入时延与元数据实时性来换写放大，可以接受；
牺牲数据完整性来换性能，不可以接受。

## 1. 术语与所有权

| 实体 | 谁持有 | 说明 |
|---|---|---|
| 文件（磁盘） | 无人 / GUI / 守护进程 | **写者唯一**；读者可并发（§3） |
| 槽 slot | 文件内两页 | 每槽一份**完整设置快照**，seq 大者生效（§2.4） |
| 本地文件标签 `local-file` | GUI 进程内 | 只读，不经过守护进程 |
| 会话 session | 守护进程 | `kind=live`（有进程写）或 `kind=replay`（只读） |
| 会话设置 | 推送后：守护进程 | 端口参数、模式、记录开关、文件参数 |
| 界面设置 | 永远 GUI | 主题、字体、比例、语言、hex 样式、`drop_action` |

GUI 的 `settings/gui.ini` 只存界面设置；守护进程的 `settings/daemon.ini` 存 `[storage]` 默认值与
最近一次会话参数；文件槽里存当前设置快照（含创建时的参数）。

## 2. 文件格式（字段级）

**头部为什么用"全量快照"而不是"追加式变更日志"**（v1 → v1.2 的核心取舍）：

| 维度 | 追加式日志 | 双槽全量快照 |
|---|---|---|
| 恢复语义 | 坏 entry 之后全部丢失，需"立即压缩"补救 | 任一槽有效即完整；不存在半个状态 |
| 掉电写序 | 依赖补丁先后顺序，补丁丢了状态就错 | **快照自带全部状态，写回乱序无害** |
| 每次元数据修改 | 复制整区（7936 B）+ 翻 superblock，2 次 write | **覆盖一整页 4096 B，1 次 write** |
| 可合并 | 中间 entry 不能随便丢 | **只关心最终状态，合并天然正确** |
| 结构 | entry 类型/序号连续性/压缩触发/坏 entry 修复 | 无 |

代价：单次写入固定 4 KB（比"追加一条 40 B entry"贵），靠"元数据低频 + ≤1 次/秒合并"兜住（§2.5）。

### 2.1 布局（固定 8 KB 头）

```
0x0000  槽 A    4096 B（一整页）  ┐ 两份完整快照，seq 大且校验通过者生效
0x1000  槽 B    4096 B（一整页）  ┘ 写时总是覆盖"较旧"的那一槽
0x2000  记录区起点（固定 8192，4 KB 对齐）
```

- 没有 superblock、没有 `recordsOffset` 字段、没有 `header_kb`：**记录区起点是格式常量 0x2000**。
  好处是"槽全坏也不影响找回记录"——直接按 0x2000 开始逐条扫描即可（§2.9、§10）。
- 两槽各占一整页：写 A 不会连带弄脏 B 所在页，避免页内读改写（RMW）。
- 头部固定 8 KB，比 v1.1 的 16 KB 省一半，短会话占比因此减半。

### 2.2 槽格式（4096 B）

```
0x0000  magic     "SLOG" u32
0x0004  version   u16 = 1              （格式版本；更高版本拒绝打开）
0x0006  flags     u16 = 0              （v1 必须为 0，未知位视为无效槽）
0x0008  seq       u64 LE               ← 唯一决定新旧
0x0010  ts        u64 LE               ← Unix ms，仅展示 + seq 并列时 tie-break
0x0018  len       u16 LE               ← payload 字节数，≤ 4000
0x001A  reserved  [6] = 0
0x0020  payload   [len] UTF-8 JSON     ← 见 §2.3
0x0020+len      crc32   u32 LE         ← 覆盖 0x00..0x1F + payload（含 len 自身）
0x0024+len      endMagic "ELOG" u32
填充            0x00 直到 0x1000（整页写满）
```

- `crc32` 必须覆盖 `len`，否则"长度字段被写坏"这类损坏会绕过校验。
- `endMagic` 用来区分**"被截断"**与**"CRC 错"**：诊断信息不同，排查成本差很多。
- 单槽载荷上限 4000 B（= 4096 − 32 头 − 8 尾 − 56 余量），超了是写入方 bug，不是用户错误。

### 2.3 快照载荷（JSON）

```json
{
  "v": 2,
  "uuid": "3f2a9b1c",
  "created": "2026-10-29T14:40:01+08:00",
  "app": "0.8.3",
  "port": "COM12", "baud": 115200, "dataBits": 8,
  "stopBits": "1", "parity": "none", "flow": "none",
  "mode": "single", "portB": null, "baudB": null,
  "encoding": "utf-8",
  "label": "COM12 @ 115200",
  "notes": "",
  "record": true,
  "origins": ["gui-a3f1", "cli-7b2c"],
  "stats": {"entries": 123456, "lastTs": 1730000000000}
}
```

| 字段 | 可变 | 约束 |
|---|---|---|
| `v`（载荷版本） | 否 | == 2；未知版本 → 该槽无效 |
| `uuid` / `created` / `app` | 否 | 必须存在；`created` 为 ISO-8601 带时区 |
| 端口参数（`port/baud/…/baudB`） | 是 | 重连、换端口、改参数后更新 |
| `label` | 是 | ≤ 256 B（UTF-8），写入前校验 |
| `notes` | 是 | ≤ 1 KB，写入前校验 |
| `record` | 是 | 当前是否在记录（仅崩溃后供人参考，不驱动自动恢复） |
| `origins` | **只追加** | 位置数组，id = 下标 + 1；不重排、不删除；追加时去重 |
| `stats` | 是 | **仅** 关闭 / 推送移交前写；不允许定时写 |

**`origins` 的容量规则（两条上限，取小者）**

- **硬上限 254 条**：`originId` 是 u8，255 保留给"内联回退"，所以 id 最多到 254。
- **字节预算 4000 B**：序列化后 `len` 必须 ≤ 4000；追加新来源会超限时同样冻结字典。
- 触发任一上限后：**冻结字典**，此后新来源一律用 `originId = 255` 内联（每条约 +14 B，见 §2.6）。
- 典型容量：base 约 450 B，余量约 3.5 KB；9 字符来源名约 290 个（被 254 条硬上限先卡住），
  16 字符约 180 个（被字节预算先卡住）。
- **绝不删除或重排**字典项：已有记录按 id 引用，删一条会让那些记录永久不可解。
- 同一字符串复用同一 id，不重复占号（追加前查重）。

### 2.4 校验与选槽

**读取流程**

```
1. 读 0x0000 与 0x1000 各 32 B（只要槽头），必要时再读整槽
2. 逐槽校验：magic == "SLOG" / version == 1 / flags == 0 / len ≤ 4000
             / 0x20+len+8 ≤ 4096 / crc32 匹配 / endMagic == "ELOG"
             / payload 能解析成 JSON 且 v == 2、uuid 与 created 存在
3. 选槽：两槽有效 → seq 大者；seq 相等 → ts 大者；ts 也相等 → 取 A
         一槽有效 → 用它
         两槽都无效 → 拒绝打开（但记录区仍可从 0x2000 扫描救回）
```

- 选槽规则必须**确定性**，禁止"随机挑一个"或"按文件顺序挑"。
- 校验失败的槽**不修复、不删除**，它保留的是上一次的完整状态，是回退依据。
- 若槽里 `payload.v` 比本程序支持的新（例如 3）：该槽无效；两槽都新 → 提示"由更新版本创建"。

**为什么不需要"翻指针"**：写新快照时另一槽仍然完整有效，不存在"指针指向半个区"的中间态；
读取方按 seq 选，写入方按 seq 覆盖（§2.5）。掉电最多让新槽无效，旧槽继续生效。

### 2.5 写槽流程

```
1. 状态 S = 当前完整设置（内存结构体）
2. 序列化 JSON → len（≤ 4000；超了就按 §2.3 冻结字典后重试）
3. target = 两槽中 seq 较小的那个；无效槽优先当 target
4. newSeq = max(有效槽 seq) + 1（都无效则 1）
5. 组装 4096 B 缓冲：头 + payload + crc32 + endMagic，其余补 0
6. 一次 pwrite(4096, target 页)；fsync 仅当 [storage] fsync = true
7. 成功后更新内存里的 seq 与当前状态
```

- **必须整页覆盖（4096 B）**：只写有效长度会留下旧尾巴，逻辑上虽被 `len` 截断，但设备层
  会做"4 KB 读改写"（物理 8 KB），比整页写 4 KB 更贵。
- **不 fsync 也安全**：目标槽写坏 → CRC/endMagic 失败 → 读取方回退另一槽；这与 v1.1
  "先复制区再翻 superblock"等价，但只有一次写。
- **合并写入天然正确**：写协程每秒最多落盘一次，期间多次状态变化只写最终状态（全量快照不含历史）。
- 写失败（EIO/ENOSPC）：旧槽仍有效，元数据回退到上一次；记日志、报错、**不停止记录**。

**写入频率约束**：一个会话的元数据写次数 = 开记录(1) + 新来源(每个 1) + 改参数(0–n) + 关记录(1)。
典型 2–4 次 × 4 KB ≈ **8–16 KB/会话**；守护进程侧合并后上界为 **1 次/秒**。
禁止定时写 `stats`、禁止按包更新 `stats`（那会把 4 KB 变成每秒 4 KB 的常流）。

### 2.6 记录格式（区域从 0x2000 开始）

```
记录 = ts u64 LE | dir u8 | len u16 LE（bit15 = 带 origin）| payload[len] | [originId u8 | 内联]
dir: 0=system 1=rx 2=tx 3=P1 4=P2 0x7F=填充（读取侧跳过）
payload: 数据方向 = 原始字节（raw，不存 hex）；system = UTF-8 文本
len ≤ 16384（bit15 留给 origin 标志，15 位 = 32767，这里主动压到 16 KB）
ts: 写入侧强制单调（now ≤ last 时写 last+1），避免 NTP 回跳把按时间分页搞坏
originId: 1..254 查槽内字典；255 = 回退，后跟 originLen u8（≤ 64）+ UTF-8 字符串
```

**填充记录**：`dir=0x7F`、`payload` 全 0、`len` 为填充内容长度。只用于把 EOF 补到 4 KB 边界（§2.7），
不计入条目数、不参与搜索/导出。

**compact 设计（21 B 小帧 → 33 B/条）**

- 载荷存**原始字节**而不是 hex：小帧体积直接减半；`session.history` 等 IPC 仍输出 hex（读取层转换）。
- **origin 字典在槽里**（`origins` 数组），记录里只存 1 字节 id；首次出现新来源时写一次快照。
- 字典满（§2.3 两条上限）后新来源用 `originId=255` 内联，常见场景不会触发。
- 时间戳用完整 u64。**注意**：增量编码可再省 4 B/帧，但会让崩溃后的记录区扫描失去时间锚点，
  且时间锚点必须依赖头部（头部丢了就没时间），收益（约 4 B/条）不值这个代价，留待 v3 再评估。
- **记录区不做逐条 CRC**：包格式自带长度字段、尾部半包按规则截断；逐条加 4 B 会让 33 B/条
  变成 37 B（+12%）。代价是位翻转会表现为"数据错"而不是"读到报错"——串口调试场景可接受，
  需要更强校验时见 §14 待定项。

### 2.7 写入策略（页对齐 + 批量 + 零 fsync）

```
缓冲 = batch_kb（默认 8 KB，范围 4~64，必须是 4 KB 的倍数）
  缓冲满          → 一次 write()（整段一次系统调用，不拆多段）
  距上次 flush ≥ flush_max_ms（默认 1000；0 = 只在满页/显式动作时写）→ write()
  显式 flush：关闭、停录、推送移交、导出与搜索前、崩溃恢复后
  fsync：默认只在 关闭 / 停录 / 推送移交 三个点；
         [storage] fsync=true 时才每次 flush 后 fsync（SSD 上代价高，默认关）
```

**为什么这么定（写放大的真实来源）**

1. **每次 `write()` 都会让 NTFS 更新文件长度/时间戳并写 `$LogFile`**，代价与调用次数相关、
   与字节数关系不大。所以压调用次数比压字节数更值钱。
2. **页内重写（RMW）**：不到 4 KB 的追加会反复重写同一个 4 KB 页。低速率设备（200 B/s Modbus 轮询）时：

| `flush_max_ms` | 每次写 | 同一页被写回 | 物理放大 |
|---|---|---|---|
| 200 | ~40 B | ≈25 次 | **≈25×**（4 KB/s 换 200 B/s） |
| 1000（默认） | ~200 B | ≈5 次 | ≈5× |
| 5000 | ~1 KB | ≈4 次 | ≈4× |
| 0（满页才写） | 4 KB | 1 次 | **1×**，代价是 ≤21 s 的数据窗口 @200 B/s |

（回写间隔取量级：Windows 脏页回写数秒级，Linux `dirty_writeback` 默认 5 s / `dirty_expire` 30 s。
上表只用来说明量级，不精确到毫秒。默认取 1000 是"≤1 s 可见"与"≈5× 放大"的折中；
纯长时间泡机、可接受长窗口的场合建议设 0。）

3. **页对齐怎么维持**：记录区起点 0x2000 是 4 KB 对齐 + `batch_kb` 是 4 KB 倍数 + 每次整段写 →
   正常追加全程对齐。**唯一破界点是关闭时那次不满页的 flush**。
4. **续写补齐对齐**：`openAppend` 后先写一条填充记录，把 EOF 补到下一个 4 KB 边界
   （所需字节 < 11 B 时再多补 4 KB，保证能容纳一条记录的 11 B 头）。成本 ≤ 4 KB / 次开会话，
   换整场 1× 写放大。读取侧按 `dir=0x7F` 跳过。
   注意：同一文件反复开关会按次累积（每次 ≤4 KB），文档与界面都要如实说明，不做隐藏。
5. **显式不做**：
   - 预分配（`SetEndOfFile`/`fallocate` 预留 512 MB 等于立刻写 512 MB 零）；
   - `mmap` 写入（脏页回写时机不可控，写放大不可控）；
   - 写到压缩卷 / EFS / 网络盘（检测到则告警；写模式默认拒绝，见 §3）。
6. **稳态代价**：零 fsync、每次写入 ≥4 KB 且页对齐、一次系统调用。
   115200 合包后约 12.3 KB/s → `batch_kb=8` 时约 **1.5 次写/秒**。

**其余约定**

- **槽可变、记录区只追加**：设置通过整页覆盖槽更新，不碰记录区；记录区永远顺序追加。
- **尾部半包**：读时跳过；写模式打开时按 §2.9 截断到最后一条完整记录。
- **不轮转**：超过 `max_size_mb` 停止记录并告警（保持"一个标签一个文件"的身份），由用户决定
  新建会话或调大上限。
- **可读性**：raw 载荷无法直接 `grep`；人读场景走导出（log/txt/csv），旧 `history/*.log` 仍是 hex。

### 2.8 索引：无 sidecar

打开时顺序扫描记录区，在内存里建索引——每 512 条记一个锚点 `{offset, ts, n}`，
索引只服务时间定位与分页，**不落盘**。

- 扫描成本：512 MB ≈ 0.5 s、4 GB ≈ 4 s（SSD 冷缓存，顺序读）；
- 每次打开都重建，因此**不存在"索引损坏/缺失"这种状态**；
- 关闭/崩溃都不需要维护索引，少一整类故障；
- 若以后实测"超大文件打开太慢"，再引入**可选**的文件内检查点记录（不是 sidecar）。

### 2.9 打开与关闭流程

```
写模式打开（openAppend）：
1. 读两槽头（各 32 B）→ 按 §2.4 选槽 → 解析 payload 得到设置
2. 两槽都无效 → 拒绝打开（记录区仍可"救回导出"，见 §10）
3. 扫描记录区尾部：若有半条记录 → 截断到最后一条完整记录（SetEndOfFile；有截断则 fsync）
4. EOF % 4096 != 0 → 写一条填充记录补齐到页边界
5. 若 record 状态与用户意图不符（例如「由文件开始」要续录）→ 写一次快照
6. 返回设置 + 条目数（来自扫描）

只读打开（openRead）：
1. 同上 1–2；不写任何字节
2. 扫尾部只做"截断位置"标记，供分页用
```

**没有 `clean` 位**（v1.2 删除）：它的信息量只有"上次是否正常关闭"，而这件事
打开时扫一遍尾部就能知道（尾部有半条 = 上次不正常）。删掉它省掉"打开写一次、关闭写一次"的
两页写入，也少一个可能与现实不符的状态位。

```
关闭（停录 / 关闭标签 / 推送移交）：
1. flush → fsync
2. 写一次快照（record=false，带 stats）
3. 关闭句柄
```

**新建文件**：一次 write 写满 8 KB 头（槽 A 有效、seq=1，槽 B 全 0），再开始追加记录。
不要只写槽 A 就停——那会让 0x1000–0x2000 变成空洞，虽然读出来是 0，但文件布局不干净、
也少了一处"槽 B 是可写目标"的显式初始状态。

### 2.10 容量与上限

- 偏移 u64 → 理论 16 EB；单条记录 ≤ 16 KB。
- 固定开销：头部 **8 KB** / 文件（两槽），无 sidecar。
- 文件系统：NTFS/exFAT 不受限；**FAT32 单文件 4 GB − 1 字节**，`sessions/` 在 FAT32 上时
  硬上限 4 GB 并提前告警。
- 默认软上限 `max_size_mb = 512`（达到即停录告警），建议硬上限 4096 MB。
- 增长速率：**合包后 ≈1.01–1.07×**，逐帧成条（最坏）≈1.57×（= 33 B / 21 B）。

| 波特率 | 原始速率 | 合包后（16 ms 窗口） | 逐帧（最坏） | 512 MB 可录（合包 / 逐帧） | 4 GB 可录（合包 / 逐帧） |
|---|---|---|---|---|---|
| 115200 | 11.5 KB/s | ≈12.3 KB/s（1.07×） | ≈18.1 KB/s（1.57×） | 12.2 h / 8.2 h | 97 h / 66 h |
| 230400 | 23.0 KB/s | ≈23.8 KB/s（1.03×） | ≈36.2 KB/s（1.57×） | 6.3 h / 4.1 h | 50 h / 33 h |
| 921600 | 92.2 KB/s | ≈92.9 KB/s（1.01×） | ≈144.8 KB/s（1.57×） | 1.6 h / 1.0 h | 12.8 h / 8.2 h |

（合包窗口取守护进程现有行为量级；若实际窗口不同，两张口径按比例换算即可。）

## 3. 锁与独占（写者互斥、读者共存）

**问题背景**：`CreateFileW(share=0)`（连读都不许）会把杀毒扫描、备份、系统搜索索引全部挡在门外，
部分安全产品会拦截或反复重试，把"安全设计"变成"兼容性故障"。

**规则**

```
Windows
  写者：CreateFileW(GENERIC_READ|GENERIC_WRITE, dwShareMode = FILE_SHARE_READ)
  读者：CreateFileW(GENERIC_READ,               dwShareMode = FILE_SHARE_READ|FILE_SHARE_WRITE)
Unix
  写者：O_RDWR|O_CREATE + flock(LOCK_EX|LOCK_NB)
  读者：O_RDONLY        + flock(LOCK_SH|LOCK_NB)
```

- **两个写者仍然必然互斥**：写者的 share 不含 `WRITE`，第二个写请求（需要 `GENERIC_WRITE`）直接被拒。
- 读者可以并发：读方按 §2.4/§2.6 规则容忍半包尾与坏记录，不依赖"文件已关闭"这一前提。
- 附带能力：本地标签可以只读跟随一个正在被守护进程写的文件（可选，每 500 ms 重扫尾部）。
- 不用 `LockFileEx`、不用 `.lock` 文件：崩溃时由 OS 释放，无残留锁。
- **网络盘（UNC）与压缩/EFS 卷**：写模式默认拒绝（`[storage] allow_network_dir=true` 可强行放行），
  读模式允许。理由：SMB 的共享语义、`fsync` 语义与追加语义都不能保证 §2.4/§2.7 的不变量。
- **同一进程**：内存表记录已打开路径，重复写打开直接拒绝（读打开允许）。
- **错误**：`errFileLocked{path, mode, holderHint}`；GUI 文案"文件已被占用（GUI / 守护进程 / 其他程序）"。

## 4. 守护进程会话模型

- 现有 `Process`（live）增加 `record bool` 与 `fileWriter`（写句柄）。**句柄只在单一写协程内使用**。
- 新增 **写协程**（每个录制会话一个）：从 channel 收 `{records, settings, flush, close}`，负责：
  1. 按 §2.7 合并刷记录缓冲；
  2. 把设置快照合并到 ≤1 次/秒落盘（只写最终状态，天然可丢中间态）；
  3. 处理写错误（失败 → 停录 + 事件）。
  这既是并发安全的前提，也是"合并写入"落地的地方。
- 新增 `ReplaySession`：`id = "file-<uuid8>"`、`path`、读句柄、槽设置、内存索引（§2.8）、分页游标。
- 统一历史来源接口 `historySource`：
  - `ringSource`：live 会话，读 5 MB 共享内存环（现有逻辑）。
  - `fileSource`：replay 会话，按内存索引直接分页（不建环、不占 5 MB）。
- `process.list` 合并两类，条目带 `kind`（`live`/`replay`）、`sessionFile`、`record`、`created`、`entries`；
  replay 条目 `status="replay"`、无 `connected`。
- `fileIndex[path]` → sessionId：同一文件只允许一个会话，重复 `history.open` 返回既有 `sessionId`（`reused=true`）。

## 8. 状态机与锁交接

```
无文件 ──开启记录──▶ recording(live) ──关闭记录/断开──▶ closed(clean|unclean)
   ▲                        │                                  │
   │                        └──── 崩溃/断电 ────────────────────┘
   │                                                           │
   └──── 新建会话（单端口/转发）        closed ──history.open──▶ replay ──push/attach──▶ recording
```

- 本地标签：`local-readonly` ──推送成功──▶ `replay`（守护进程）──attach──▶ `live`。
- 推送是**锁交接**，时序必须确定：

```
local-held ──flush+fsync──▶ releasing(close 句柄) ──▶ history.open
   成功 → daemon-held（之后 GUI 一律走 IPC）
   失败 → 查 history.files：
            file.locked 且被守护进程持有 → 直接开 replay 标签（不重复抢锁）
            否则重试 3 × 200 ms
              仍失败 → 重新获取本地锁，标签留在本地只读，提示"被其他程序占用"
```

- 交接窗口里第三方抢占只可能发生在 `close` 与 `open` 之间，重试 + 查询足以收敛；
  不做 `.lock` 占位文件（崩溃残留的代价比这个窗口大）。
- 记录开关：开 → 无文件则建（一次写满 8 KB 头：槽 A 有效、槽 B 全 0），有文件则补齐对齐后追加；
  关 → flush + fsync + 写一次快照（record=false）+ 关闭、保留文件。

## 10. 错误与边界

| 场景 | 行为 |
|---|---|
| 文件被其他写者占用 | `file_locked`，提示"文件已被占用（GUI / 守护进程 / 其他程序）" |
| 文件被守护进程占用，GUI 拖入 | 若 `drop_action=push` 或点推送 → 复用已有会话；否则提示"已被守护进程接管" |
| 魔数不对 / 不是本格式 | 尝试 legacy 只读路径，失败则报错 |
| 单槽损坏（CRC / endMagic / len 越界 / JSON 坏） | 该槽作废，用另一槽；**不修复、不覆盖**损坏槽（留着做回退依据） |
| 两槽都坏 | 拒绝打开（设置不可信）；**记录区仍可从 0x2000 扫描做"救回导出"** |
| 槽版本更高（`version` 或 `payload.v`） | 该槽无效；两槽都高 → 提示"由更新版本创建" |
| 快照序列化后 > 4000 B | 冻结 origins 字典、新来源改内联；仍超则拒绝写入并报错（属 bug，不是用户错误） |
| 打开时尾部有半条记录 | 截断到最后完整记录、记日志、继续 |
| EOF 未按 4 KB 对齐 | 写一条填充记录补齐（每次开会话最多 4 KB） |
| 记录区中间出现坏记录 | 读到该处即停（不猜、不跳），已读部分正常展示 |
| 磁盘满（`ENOSPC`/`DISK_FULL`） | 停录、flush 能写的部分、发事件、状态栏告警；文件保持可读可导出 |
| 可用空间 < `min_free_mb` | **写前**检查（每 64 MB 或每 30 s 一次），提前停录并告警 |
| 达到 `max_size_mb` | 在**下一批写入前**停录并告警，不写出超限的那一页 |
| 写入返回 I/O 错误（EIO 等） | 停录、关闭句柄、会话保留但标 `record=false`，事件提示"写盘失败" |
| 推送失败（第三方抢占 / 守护进程拒绝） | GUI 重试 3×200 ms → 重新获取锁、标签留在本地只读、提示原因 |
| 导出失败 | 先写 `*.tmp`，成功后 rename；失败删除 tmp，不留半个文件、不覆盖原文件 |
| 超大文件 | 按页读 + 内存索引定位，不整文件进内存；扫描耗时见 §2.8 |
| 网络盘 / 压缩卷 / EFS | 写模式拒绝（可配放行），读模式允许 |

## 11. 兼容与迁移

- 老 `history/*.log`：hex 载荷、无 `SLOG` 头 → 走 legacy 只读路径，可离线打开、可 replay、可导出；
  不可作为 live 追加目标。
- 新 `.stlog`：raw 载荷 + origin 字典；IPC 输出仍统一 hex（读取层转换），前端与 CLI 看到的 JSON 形状不变。
- `history.attach`（现有）保留，行为等价于「由文件开始」的 replay 分支。
- 不自动转换历史文件；需要时用 `export` 转 csv/txt 再迁。
- 格式版本策略：`version=1` 固定布局（记录起点 0x2000）；未来若布局要变，升 `version` 并拒绝旧程序写入。

## 12. 测试计划

**槽与恢复（v1.2 重点）**

- 槽校验逐项：magic / version=2 / flags≠0 / len>4000 / `0x20+len+8>4096` / crc 错 / endMagic 错 /
  JSON 坏 / payload.v=3 → 该槽无效；
- 选槽：两有效取 seq 大；seq 等取 ts 大；再等取 A；一有效用它；都无效拒绝；
- **torn write**：把槽截断到 0..4095 的抽样长度（如 0/1/32/33/34/2048/4095），
  写模式必须回退另一槽且设置完整；
- **写乱序**：先写 seq 11 到 B、再补写 seq 10 到 A（模拟回写乱序），选中结果必须是 seq 11 且状态正确；
- 写槽：target 必须是 seq 较小者（无效槽优先）；`newSeq = max+1`；断言每次写入恰好 4096 B；
- 快照预算：origins 追加到第 255 条（硬上限）或超 4000 B（字节预算）→ 冻结字典、新来源内联、
  旧记录仍可解；同名字符串不重复占号；
- 无 `clean` 位：只读打开不写任何字节；写模式打开只在状态变化时写；关闭写 1 次；
- 记录区起点：两槽全坏时仍能从 0x2000 扫出记录并导出。

**记录与批写**

- 解析：raw 载荷、system 文本、`dir=0x7F` 填充跳过、半包、坏包、`len` 越界、origin 255 内联；
- 时间戳：写入侧单调钳制（注入回拨时钟）；
- 批写：缓冲满触发一次 write（断言调用次数）；`flush_max_ms` 用可注入时钟；显式 flush 点；
  崩溃丢 ≤ `batch_kb`；重开截断半条；EOF 补齐 4 KB 对齐；
- `fsync=false` 时稳态 fsync 次数为 0（关闭/停录/移交除外）。

**锁**

- 写-写互斥（两进程，第二个必须失败）；写-读并发（读者能在写者持有句柄时打开，
  读到一半的尾部必须"停"而不是报错）；读-读并发；同一进程重复写打开被拒。

**磁盘与故障**

- 模拟 `ENOSPC`：停录 + 事件 + 文件仍可读可导出；可用空间低于 `min_free_mb` 时提前停录；
- 槽写失败（注入 EIO）：旧槽继续生效、记录不中断、事件可见；
- 只读卷 / 无权限目录：建文件失败的错误信息可读、不崩。

**安全**

- 恶意文件（巨型 `len`、`seq` 全 1、坏 JSON、超长 label、`origins` 上千条、保留名/路径穿越文件名）
  → 不崩、不越界、不无限循环；
- CSV 导出对 `= + - @` 开头的单元格加前缀（防公式注入），引号/逗号/换行正确转义；
- 导出走 tmp + rename，失败不留残件。

**集成**

- 守护进程建会话 → 开记录 → 写 → 关 → 重开续写；`history.open` replay 分页；
- 推送（GUI 释放 → 守护进程获取），含"交接窗口被第三方抢占"的失败路径；
- CLI/MCP 检索打开；GUI 拖入离线只读 + 导出；槽里的端口参数预填「由文件开始」；同一文件二次写打开被拒。

**性能**

- 230400 合包后 ~60 包/s 连跑 1 小时：约 **21.6 万条、约 82 MB**（60×3600×396 B ≈ 85 MB）。
  统计 `write()` 次数（目标 ≤ 1.5 次/s @ `batch_kb=8`）、fsync 次数（稳态 0）、CPU 与 UI 延迟；
- 元数据写：一次会话应 ≤ 4 页（16 KB），并断言没有定时写；
- 1 GB 文件打开扫描耗时（目标 ≤ 1 s 热缓存）与分页、流式导出；
- `batch_kb=4/8/16` × `flush_max_ms=0/200/1000/5000` 组合对比：记录写调用次数与进程 I/O 计数。

## 14. 风险与待定

1. **`process.list` 混入 replay** 对现有 `syncDaemonSessions` 的改造量（GUI 目前把所有进程当会话标签处理）。
2. **并发读的期望管理**：读者可能读到"半个包"，前端必须表现为"实时追加中"而不是数据错误；
   需要 UI 文案与刷新节奏（500 ms）约定。
3. **元数据写固定 4 KB**：短会话（100 条 ≈3 KB 数据）要付 1–2 页元数据，占比偏高。
   这是页粒度的下界，只能靠"状态没变就不写"压缩，不打算再优化。
4. **快照预算**：`origins` 上限 = min(254 条, 4000 B)，短名 254 条封顶、16 字符名约 180 条；
   超出后新来源内联（每条约 +14 B）。极端场景（GUI 反复重连产生大量不同 origin）需实测触发频率。
5. **反复开关同一文件会按次补页**：每次 ≤4 KB；打开 100 次的累积开销可感知，需在导出/界面口径里说明。
6. **冷缓存打开 4 GB ≈ 4 s**：可接受，但频繁来回切大文件会觉得慢；v2 再评估文件内检查点。
7. **`flush_max_ms=0` 的数据窗口**：低速率下可达 20 s（200 B/s 填满 4 KB）。默认 1000 是折中。
8. **`write()` 次数**在真实 NTFS 上的收益需实测（1.5 次/秒是理论值，含合包假设）。
9. **无 `clean` 位**：无法区分"崩在 flush 前（没有半条）"与"正常关闭"，只能靠尾部半条判定；
   因此"上次未正常关闭"的提示只在能看出痕迹时出现。
10. **记录区无逐条 CRC**：位翻转表现为数据错。若以后需要，可在文件内每 N KB 插一条聚合校验记录
    （成本约 4 B/N KB），但要新增记录类型，v1 不做。
11. **大文件导出**时间与内存（流式 + 进度事件）。
12. **「由文件开始」的参数预填**：槽里参数可能过时，连接前允许用户改。
13. **raw 载荷不可 grep**：人读依赖导出；若需外部工具直接解析，补一份 RFC 风格格式规范。
14. **头部固定 8 KB**：未来扩展靠 `version` 升版，不做"向前兼容地塞新字段进槽"。
15. **网络盘/压缩卷不支持写**：明确拒绝并提示，不做"尽力而为"。
16. **杀毒软件对 `FILE_SHARE_READ` 的处理**需真机实测。

| # | 项目 | v1.1 | v1.2 |
|---|---|---|---|
| 1 | 头部结构 | 双 superblock + 双追加区（变更日志） | **双槽全量快照**（各 4 KB，占整页） |

| 4 | 元数据修改 | 复制整区 + 追加 entry + 翻 superblock（2 次写，7936+128 B） | **整页覆盖旧槽（1 次写 4096 B）** |
